# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` (`order_mgmt_mfe`)
Module Federation remote, or when standing up a NEW remote for a bounded
context that doesn't have one yet. This is the Vite/React micro-frontend
layer that `warehouse-console` (the shell) lazy-loads as `order_mgmt_mfe/App`
at `/order-management` — see that repo's own MFE-remotes rules for the
shell-side half of this contract.

## `web/vite.config.ts` must stay in OBJECT form, always

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/order-management/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  plugins: [react(), federation({ name: "order_mgmt_mfe", /* ... */ })],
  // ...
});
```

This repo's own `web/vite.config.ts` already documents this trap in its
top-of-file comment — read it before touching the file. Never convert this
to the callback form (`defineConfig(({ command }) => ({...}))`) to compute
`base` dynamically. `web/vitest.config.ts` does `mergeConfig(viteConfig,
defineConfig({...}))`, and Vite throws `Error: Cannot merge config in
form of callback` on a function export — killing the ENTIRE test suite
for a one-line config change, not just a new test.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After a build with the `/mfes/order-management/` base (set by
`IS_BUILD`/`PUBLIC_BASE` above), `dist/remoteEntry.js` is small and
imports a RELATIVE path — grepping it for `/mfes/order-management/`
returns zero matches. That is expected, not a bug: `dist/index.html`
carries the absolute prefixed URLs, every JS chunk uses relative ESM
imports, and the module-preload helper resolves relative to wherever
`remoteEntry.js` was actually fetched from — exactly what a path-mounted
remote needs. Verify correctness by serving the built image and fetching
through the real gateway path, never by grepping the built file for the
expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"file:../../warehouse-ui-kit"`. Any
domain-status color, chart, or shared layout primitive belongs in that
repo, not hand-rolled here — a remote reinventing its own palette instead
of consuming `StatusPill`/`tokens.css` is a bug, not a style choice
(visual consistency across the MFE boundary is the #1 place MFE UX
fails).

## Give the remote a `test` script, or added tests silently never run

`npm test` must map to `vitest run` in `web/package.json` — this repo's
already does (`"test": "vitest run"`), but confirm it hasn't regressed
before assuming a new `.test.ts` file is actually executing. Several
remotes across this fleet have historically shipped `package.json` with
only build/dev/lint/preview scripts, silently swallowing any test file
someone added later. Also confirm this repo's CI does NOT currently gate
`web/` at all: grepping `.github/workflows/ci.yml` for `web/`/`npm run`
finds nothing — a green PR here proves the Go side passed, not that the
frontend builds or tests. Before merging any PR touching `web/`,
independently run `npm ci && npm run lint && npm run build && npm test`
yourself rather than trusting CI's green checkmarks.

## The Docker build recipe (packaging as a deployable nginx workload)

Three traps, in order of how much time they cost when hit blind — see
this repo's own `web/Dockerfile`, which documents all three inline:

1. **Base image must be `node:22-bookworm-slim`, not an alpine or newer
   node image.** This repo's `web/package-lock.json` was generated by
   npm 10 and carries no Linux entries for Vite's platform-specific
   optional dependencies (`@rolldown/binding-linux-*`,
   `lightningcss-linux-*`). npm 11 rejects that lockfile outright with
   `EUSAGE "lock file out of sync"`; glibc (not musl) is what matches the
   published `*-gnu` bindings.
2. **Do NOT install from the committed lockfile, and do NOT reuse a host
   `node_modules`.** Both leave the native binding missing
   (`Cannot find native binding ... @rolldown/binding-linux-*`, a known
   npm/cli optional-dependency bug, npm/cli#4828). The working recipe,
   exactly as `web/Dockerfile`'s builder stage does it: `rm -rf
   node_modules package-lock.json` in the ui-kit build stage (it arrives
   as a named BuildKit context from a developer checkout), `COPY
   package.json ./` only, then `npm install --no-save`.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency:
   ```bash
   cd web
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/order-management-frontend:local .
   ```

See `web/Dockerfile`'s complete, working, heavily commented recipe — copy
it rather than re-deriving these three traps from scratch for a new
remote in another repo.

## Wiring into `warehouse-infra`'s deploy

A new remote isn't deployed automatically — `warehouse-infra`'s
`local.services` map and this repo's own Helm chart (`charts/order-management`,
`frontend.enabled` value, default `false`) both need updating. See
`warehouse-infra`'s AGENTS.md for the Terraform side of this; this repo
only needs to ship a working chart with `frontend.enabled` wired to a
toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

CI's Go-side jobs do NOT reproduce this sequence (see above — `web/` is
untested by CI in this fleet as of this writing). Run it yourself, and if
verifying a PR from a worktree, remember `@warehouse/ui-kit`'s relative
`file:../../warehouse-ui-kit` dependency only resolves when the worktree
is a sibling of `~/warehouse-systems/warehouse-ui-kit`, not an isolated
`/tmp` checkout.
